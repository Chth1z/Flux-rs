## 3 技术评估

### 3.1 架构与设计：强

设计层面几乎没有可挑剔之处，这不是客气话，而是有具体依据的：

- **问题定义克制。** PHIL-0 把产品收缩到一个问题——「这个包属不属于被选中的 app」——并把路由、规则、DNS 全部留给官方 sing-box。§19 列出的 30 余条被拒方案（cgroup SOCK_ADDR、iptables TPROXY、TUN、SOCKMAP、patch sing-box、多后端……）每条都有源码级或实测级的否决依据，不是拍脑袋。
- **失败语义诚实且精确。** admission-bounded fail-open：入场前任何失败走 Direct（`TC_ACT_UNSPEC` 而不是 `TC_ACT_OK`，理由是不能截断 AOSP CLAT 与 OEM 的后续 classifier）；入场后任何失败 `TC_ACT_SHOT`，绝不回落到真实目的地。README 与 guide 把不能做到的事（Private DNS、`enforce_dns_uid`、流量统计翻倍、engine 活锁不可检测）写在最前面。
- **所有权靠证明不靠记账**（PHIL-5）。删内核对象前按 netns / ifindex / ifname / parent / chain / pref / handle / kind / direct-action / 程序名 / map 集全字段比对，dump 两次不一致即拒绝——这直接吸取了对照项目 `AndroidTProxyShell` 与 `box4magisk` 的事故。
- **机制与策略分离**（PHIL-1）。bypass 前缀被打上 `RESERVED` / `POLICY` 标签，用户的 CIDR 白名单可以表达而不会反转机制自己的保留段；listener 地址、veth 名、TC handle 一律不暴露给用户。
- **平台事实的证据链完整。** `bpf_sk_assign()` 在 6.5 之前拒绝 `SO_REUSEPORT`、`IN_DEV_RPFILTER` 取 `max()` 而 `ACCEPT_LOCAL` 取 `or()`、`fchown()` 使 per-app DNS 零额外机制可行——每条都指向内核或 AOSP 的具体文件与版本。

### 3.2 数据面（`bpf/flux.bpf.c`、`flux_abi.h`）：强

- 877 行 C，顶部的契约注释按 AUTH-5 的说明「刻意冗长」，因为违反它的症状是**静默泄漏用户流量**而 verifier 与编译器都不报错。这是全仓库最值钱的一段注释。
- 14 条 verifier 陷阱（§7）与 11 条加载器加固（§12）逐条落地，包括 `bpf_sk_lookup_*` 引用在每条分支恰好释放一次、禁用带返回值的原子操作（arm64 5.15 上 `-ENOTSUPP`）、`-mcpu=v3` 固定。
- ABI 是单一真相源 + 手写镜像 + 三重校验：`abi.rs` 单测守镜像侧，`cargo xtask abi-check` 让 clang 用 `_Static_assert` 核对每个 size/offset，`btf-check` 比对手写 BTF 与 `.BTF` 段。CI 的 verifier gate 用固定版 bpftool 真加载四个程序——这条门禁在第一次启用时就抓到「四个段名 libbpf 一律拒绝」的真 bug。

### 3.3 守护进程（`crates/fluxd`）：正确性有保障，结构有债

**做得好的：**

- 单线程 epoll reactor，八个事件源（signalfd、inotify、rtnetlink、pidfd、BPF ringbuf、timerfd、控制 socket、订阅 eventfd），**无周期轮询**（PHIL-3）。订阅抓取放工作线程并通过 eventfd 回到主循环，是「既有形状的又一个实例」而不是新机制。
- 约 110 处 `unsafe`，**全部带 `SAFETY:` 注释**——`undocumented_unsafe_blocks = "warn"` 加 CI 的 `-D warnings` 把这条变成了机检。`flux-core` 则整个 crate `#![forbid(unsafe_code)]`。
- 零 `TODO` / `FIXME`；非测试代码里的 `unwrap()` 抽查（`layout.rs` 28 处）全部位于 `#[cfg(test)]` 模块。
- 模块依赖方向在 `main.rs` 顶部写成合同：`main -> reactor -> {layout, control, packages, netlink, bpf, dataplane, engine}`，raw netlink 只在 `netlink/`，raw `bpf(2)` 只在 `bpf/`。抽查符合。

**债务：**

| 现象 | 数据 | 代价 |
|---|---|---|
| 超大文件 | `reactor.rs` 4192 行；`platform.rs` 2983 行；`Reactor` 结构约 65 个字段；`converge()` 单函数约 370 行 | 任何改动都要在脑中装载整个状态机；AI agent 每次会话从零重建上下文，这个成本它付得更贵 |
| 过时的 `#[allow(dead_code)]` | `fluxd/src` 约 40 处，注释如「The Phase 5 attachment consumer is not present yet」「Phase 5 supplies program fds」——Phase 5 已于 08-27 完成 | 直接违反 GOV-4.1「`#[allow]` 必须写清为什么不适用」的精神：理由已经为假。根因见下一行 |
| 测试用 `#[path]` 直接包含源码模块 | `phase3–7_device.rs` 各自 `#[path = "../src/bpf/mod.rs"] mod bpf;` 等，把同一份源码编进 6 个二进制 | 每个二进制里未用到的项都触发 `dead_code`，只能靠 `#[allow]` 压掉；也让这些测试无法复用 `fluxd` 的编译产物 |
| 状态机零宿主测试 | `reactor.rs` 的 9 个单测只覆盖纯函数（退避表、日期、hint 组合）；§26 的三态 × 事件矩阵没有任何不上设备就能跑的测试 | 一次 reactor 重构的回归只能靠真机；而真机只有一台 |

### 3.4 纯逻辑层（`crates/flux-core`）：强

- 「可在 Windows 上全速测」的承诺兑现：无 I/O、无 `unsafe`、无平台依赖，89 个单测 0.01 秒跑完。§15 要求保留的八个逻辑测试全部存在。
- 生成是纯函数并有机检：`generation_changes_only_outbounds_and_is_pure` 把生成物的 `outbounds` 换回模板后要求深度相等、键序一致。
- 订阅 URI 解析覆盖九种协议各一例、两种输入格式判别、七步精修的**顺序**逐对测试、零节点硬错误——这是 handoff 任务书要求「测试要写厚」的地方，确实写厚了。
- 一个值得称道的判断：`snell` 被实现者（Codex）发现是 Surge 私有协议、官方 sing-box 全树零引用，于是**拒绝自行改合同而是停下报告**；所有者复核后从 §28 移除，并把不支持的 scheme 从「静默跳过」改为「整份解析失败并报行号」。这个决策链完整记录在提交说明与更正对照表里。

### 3.5 构建、打包、供应链：强，且是开源 GPL 合规的范本

- 工具链、`Cargo.lock`、NDK r27d、engine 资产（archive 与 binary 的 SHA-256 + size）、BPF ABI 全部固定。
- `cargo xtask verify-package` 做两次 clean 交叉构建并要求 ZIP 逐字节相同；打包是 **14 项精确 allowlist**，多一个文件即失败。
- `fluxd` 自身以 `p_align >= 0x4000` 链接，同时**诚实地**记录官方 sing-box 只有 `0x1000` 对齐、因此 16 KiB 页设备不受支持——而不是假装支持。
- 发布只接受**签名的 annotated tag**，且 tag 后缀必须与工作区版本相等；随 ZIP 一并发布 `engine.lock` 固定的 sing-box **Corresponding Source** 归档。这是很多分发 GPL 二进制的模块作者根本没做的事。
- `deny.toml` 把「允许的许可证列表」当作依赖树的许可证清单来维护：`unused-allowed-license = "deny"` 让每条允许项都必须被真实依赖使用。这条纪律很好，也正是它会在下次推送时抓住下面 4.1 那个问题。

### 3.6 测试与验证：分层清楚，但金字塔的中段是空的

| 层 | 内容 | 状态 |
|---|---|---|
| 宿主纯逻辑 | flux-core 89 + xtask 32 | 全绿，任何平台可跑 |
| Linux 宿主 | fluxd 单测 63 + `engine_lifecycle`、`daemon_e2e` 两个 fake-engine 集成测试 | 提交说明记录 184 项通过（WSL）；Windows 上不可跑 |
| 真机 | `phase3–7_device`（按 `FLUX_PHASE*_DEVICE_TEST=1` 与 root 门控，带 cleanup 与残留检查） | 已在 SM-S9180 / 5.15.211 / KernelSU 上跑过 Phase 3–7；**0.9.5 批次 A–C 的构建尚未真机回归**（§17.0 当日工作树的自述） |
| 模块脚本 | shellcheck + `tools/phase8/module_lifecycle_test.sh` | CI 通过 |

缺口：

- **没有 fuzz。** 三类以 root 身份解析的不可信输入——远端订阅响应（base64 / JSON / 九种 URI）、用户的 JSONC 模板、`flux.toml`——全部在 `flux-core` 的纯函数里，接 `cargo-fuzz` 的成本接近于零，收益是抓到 panic（`panic = "abort"` 意味着一个 panic 就是 daemon 退出与 5 秒内的重启风暴）。netlink dump 与 BPF ELF 解析虽在 `fluxd`，输入也可离线构造。
- **状态机没有宿主仿真。** 见 3.3。
- **单设备证据。** §16.3 的五层外推分类（AOSP 强制 / GKI / SoC / OEM / 运行期）设计得很好，但目前每一层的「实测」都来自同一台机器；「把 OEM 层观察当普适事实」被治理文档列为本项目最容易犯的错，而防它的唯一办法是第二台不同 SoC / OEM / 内核版本的设备。§20 第 10 条要求三个管理器各完成一次 smoke，现有记录只证明了 KernelSU。

### 3.7 依赖树观察

`cargo tree` 面向 `aarch64-linux-android` 显示约 70 个 crate，其中三点值得所有者知道：

1. **`webpki-roots`（Mozilla 根证书包）被编进了二进制但从未使用。** `ureq` 的 `rustls` feature 等于 `rustls-no-provider` + `_ring` + `rustls-webpki-roots`；而 `subscription.rs` 明确只读 Android 自己的三个证书目录并且「一张都没读到时硬失败，不回落到打包根证书」。二进制里躺着一份不用的信任锚，与这条政策自相矛盾，也是许可证问题的来源之一（见 4.1）。
2. **`url` 拉进了完整的 ICU/idna 栈**（`icu_normalizer`、`icu_properties`、`zerovec`、`tinystr` 等约 15 个 crate）。对一个 `opt-level = "z"` 的项目，这是值得**量一下**再决定的：如果订阅 URL 里 IDN 域名不是需求，可能有更轻的选择；如果是，就把大小写进 §14 的预算。
3. **`base64` 双版本**（直接依赖 0.23，`ureq` 依赖 0.22）与 `syn` 双版本（2 与 3）。前者改成 0.22 即可去重，后者是上游问题。

## 5 开发过程评估

### 5.1 节奏与提交

- 七天 94 次提交、4.7 万行净增，其中 08-30 一天从 10:45 到 22:37 连续 38 次提交完成了整份蓝图的折叠、英文化、治理重构与三个实现批次的前两个。这是 AI agent 驱动开发能达到的吞吐量的一个清晰样本。
- **提交说明是全仓库最好的文档之一。** 它们写「为什么」而不复述 diff，记录被推翻的结论，甚至记录实现者（Codex）两次拒绝动手的原因并判定「Both were correct」。这符合 GOV-8，而且比大多数人类团队做得好。
- 分支模型是单 `main` 直推，无 PR。对单人项目合理；仓库公开或有第二贡献者时需要改变（见 6.4）。

### 5.2 CI/CD

六个 job（fmt/clippy/test + doc-check + template-check、Windows 宿主门禁、BPF 编译 + abi-check + btf-check + verifier gate、Android 交叉构建 + 可复现打包、cargo deny、shellcheck + 模块生命周期），总耗时 2 分 48 秒，最近 12 次全绿。设计上值得注意的点：

- Windows job 的存在不是为了「多一个平台」，而是把「本地开发机能跑的最大子集」固化成 CI 的一列，并在注释里明确「A Windows pass never substitutes for the Linux workspace gate or the on-device suite」。
- 发布 workflow 对 tag 签名的校验用 GitHub API 的 `verification.verified`，同时覆盖 GPG 与 SSH 签名。
- 缺的是：**CI 从未跑过当前 HEAD**（发现 2）；没有 binary size 的跟踪（§14 有能效预算，但没有把 `fluxd` 大小与 ZIP 大小画成趋势）；没有 fuzz job。

### 5.3 开发环境

宿主是 Windows，而产品是 Android，Linux 门禁靠 WSL，真机靠 adb。项目对这条链的坑做了细致的记录（PowerShell 5.1 会毁掉 CJK、`Get-Content` 数错行、toybox `sed` 不支持 `\b` 且静默失效、`GITHUB_PATH` 只对后续 step 生效），这些「带疤的规矩」是新人和新会话最需要的东西。本次检查也**在同一个坑里摔了一次**：一条含中文说明的 PowerShell 命令因编码被解析器拒绝——证明 AGENTS.md 那条警告不是多余的。

### 5.4 AI 协作模式

这个项目的开发模式本身是值得记录的对象：

1. 所有者与 Cursor agent 写合同（`spec/`）、治理（`governance.md`）、任务书（`handoff-*.md`）。
2. 任务书把范围、合同章节、依赖白名单（GOV-1.2）、验收命令、**禁止事项**（「不要碰 `docs/spec/**`，合同有问题就停下报告」）写死。
3. 另一个 agent（Codex）实现；遇到合同矛盾停下而不是绕过。
4. 所有者复核、修正、写提交说明，把 agent 的正确拒绝与错误一并记入历史。

这条链的两个薄弱点：任务书没有进版本库（发现 13）；「复核」目前没有清单化——PHIL-10 是设计评审清单，但没有对应的**代码复核**清单（比如：新 `#[allow]` 的理由是否为真、新依赖是否过了 `deny`、散文里的数字是否有来源）。发现 1、3、6、9 恰好都是这类清单能拦住的。

## 6 治理评估

### 6.1 已经做对的

- **目录即权威等级。** `philosophy/`（判据）→ `spec/`（合同，代码错）→ `guide/`（投影，文档错）→ `history/`（记录，只增不改）→ `plan/`（会被做完）。路径本身携带「违反它意味着什么」，这是 PHIL-2 用在文档上，而且真的执行了：两份增量蓝图折叠后移入 `history/` 冻结，`plan/` 的条目做完就划掉。
- **证据纪律可机检。** 每条断言标注 Verified / Measured / Inferred；`doc-check` 校验章节映射、相对链接、四个命名空间 1217 处标识符引用、`FLUX_SEC_*` 一致性、推翻计数、`cargo xtask` 子命令真实存在、AGENTS.md 行数预算、退役编号不得出现在代码中。**每一项都对应一次真实抓到的缺陷**，文档里写明了是哪一次。
- **更正协议有产出。** `review-log.md` §0.6 的对照表已有 24 行「原说法 / 实际 / 处置」，包括「结论对但理由错」这类最容易被忽略的更正。设计推翻自己 8 次被当作优点写进蓝图开头。
- **决策权划分具体。** GOV-1.2 列出的必须问所有者的七类事（不可逆操作、改开发机、改测试机持久状态、范围变更、产品取舍、新依赖、对外表述）在实践中被遵守——订阅的四个依赖在任务书里标注「已获所有者批准」，`snell` 的移除走了更正协议。
- **许可合规超过同类。** 见 3.5。

### 6.2 风险：单点

| 单点 | 现状 | 缓解程度 |
|---|---|---|
| 一个人 | 唯一所有者与决策者；无第二 maintainer；仓库私有无社区 | **文档把知识外化得极好**，这是最重要的缓解——一个新人（或新 agent）从 `AGENTS.md` → `docs/README.md` → 蓝图能重建全部上下文。但决策权、设备、GitHub 账号、签名密钥仍在一人手里 |
| 一台开发机 | 四次提交与当日修改只在本机；WSL 与 NDK 也只在本机配好 | 推送即可缓解提交风险；环境搭建步骤散在提交说明与 AGENTS.md 里，缺一份「接手 runbook」 |
| 一部手机 | 全部 Measured 证据来自 SM-S9180 / Android 16 / 5.15.211 / KernelSU | 五层外推分类是正确的方法论，但没有第二台设备它只是方法论。三管理器 smoke（§20 第 10 条）也需要不止一种 root 方案 |
| 一个引擎版本 | `engine.lock` 固定 1.13.19；升级时要重测 `p_align`、`SO_REUSEPORT`、`q2-run-device.sh`、`template-check` | 步骤散见 §9、§17.3、`engine.lock` 注释；没有一份「升级 engine 的 checklist」 |

### 6.3 GitHub 侧

- 私有仓库、免费计划：**无法启用分支保护**，`main` 可直推、可 force-push。当前由 GOV-8「不 amend、不 force-push」的自律替代。
- 无 release、无 tag：与 §20「门禁全过才打签名 tag」一致，是有意为之，不是遗漏。
- 无 `SECURITY.md`、issue 模板、`CONTRIBUTING.md`。私有阶段不需要；公开前需要——尤其是一个以 root 运行、处理远端不可信输入的网络组件，需要一条漏洞报告通道。

### 6.4 治理规则自身的小漂移

- AUTH-0.4 的语言表与 `architecture.md` 不一致（发现 10）。
- AUTH-0.5 规定 AGENTS.md「只放路由与代码里看不出的约束」，而它当前包含会过时的统计数字（发现 9）。
- `docs/README.md` 的表把 `spec/` 标为「英文（0.9.5 起）」、`philosophy.md` 为英文，其余中文——实际执行与表一致，只有 guide 层一例外。
