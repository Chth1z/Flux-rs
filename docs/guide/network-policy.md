# 校园网排查与参考配置适配

本文回答两个问题：开启 Flux 后校园网不可用时，怎样区分问题所在；怎样把外部配置的思路用于自己的 sing-box 模板。它是操作指南，机制边界以 [`蓝图`](../spec/blueprint.md) 的 §3.6、§9.6、§28、§29 为准。

## 先区分已知事实与待验证原因

当前已知的现象是：**关闭 Flux 可以联网，开启 Flux 不能联网。** 目前没有校园网测试环境。这个现象将范围缩小到启用后经过的路径，但不足以判断是接口接管、DNS、认证还是节点协议。

`Active` 表示本地接管路径和引擎监听已就绪，不表示远端节点或互联网已经可达。

| 当时的证据 | 下一步看什么 | 能回答什么 |
|---|---|---|
| `Inactive`，带 `tc_filter`、`bpf_*` 或 listener 错误 | `fluxd status` 的具体错误和逐接口状态 | 接管/监听没有建立，不先猜 DNS |
| `Inactive`，带 `subscription_*`、`engine_config_*` | 节点输入、当前 URL 的订阅快照、引擎检查错误 | 候选是否完整，是否被远端下载依赖阻住 |
| `Active` 且校园 Wi-Fi 接口受覆盖，应用仍失败 | 引擎当时的 DNS、拨号、规则集下载错误与所选 outbound | 本地路径之后是哪一步失败 |
| 只在未认证时失败 | 认证应用是否被选中、认证目标是否依赖校园 DNS/原网络绑定 | 认证流量是否需要保留原始路径 |
| 认证后只有部分节点失败 | 同一应用、同一目标、同一校园网络上不同节点的结果 | 是否与 UDP/QUIC 或特定服务器有关；一次切换成功仍不是协议限制的证明 |

Hysteria2 使用 QUIC/UDP；校园网限制 UDP 是一个需要现场比较的假设。添加更多 DNS 备用地址不能证明或解决这类协议限制，也不能仅凭“换 TCP 能通”就归因于所有校园网都封 UDP。

现场恢复条件具备后，保留同一时段的 `fluxd status` 和 `fluxd bugreport`。诊断包默认脱敏；不需要提供完整节点 URI。将 Flux 开/关、是否已认证、所选节点和成功/失败的目标对应起来，再做一次只改变一个变量的比较。

## 认证流量由谁处理

认证页面有时绑定到正在认证的 Wi-Fi 网络。sing-box 的 DIRECT 出站会新建 root 进程的连接，不能继承原应用的 Android Network 身份。

- 需要保留认证应用的原始网络语义：在 `[apps]` 的选择中排除实际认证应用。包名以手机上的应用为准，不维护一份猜测的系统包名单。
- 需要让一个已知目的地址保持原始路径：使用 `[cidr]` 的现有直连规则；私有和本机地址已有固定旁路。
- 只希望在某个 Wi-Fi 完全不启用 Flux：使用已有 `[ssid]` 黑名单。这是你选择的长期策略，不是自动认证修复。

这些方式不要求增加“校园网模式”或第二个开关。不要在没有现场依据时把整个校园网、系统 UID 或所有 UDP 自动旁路。

## DNS 应在正确的层处理

**不要把 `type: local` 等同于 Android 系统 DNS。** 本次核对的 1.13.19 与 1.14.1 普通 bare CLI 路径读取 `/etc/resolv.conf`；它没有图形客户端提供的 Android DNS bridge，也不从 Android 当前网络的 LinkProperties 取得服务器。Flux 守护进程通过 Bionic 解析订阅域名，与 sing-box 的这个 DNS server 类型不是同一条路径。具体源码范围见研究记录末尾的 1.14.1 补充。

两种常见意图应分开表达：

| 意图 | 放在哪里 |
|---|---|
| 保持发往已知 DNS 服务器的原始查询目标 | 在现有 `hijack-dns` 前，按目的 IP/端口配置 sing-box DIRECT；如果要保留原应用网络身份，则用 Flux 的 CIDR 旁路 |
| 某些校园域名必须问校园 DNS | 在 `dns.servers` 声明已确认可用的服务器，用 `dns.rules` 按查询域名选择它；对后续连接再配置对应路由 |

`route.domain_suffix` 配合 `protocol: dns` 不能代替第二行：DNS sniff 并不会把问题中的域名写入路由层的目标域名字段。也不要猜一个公共 DoH 地址就把它叫作校园 DNS。

认证完成可能只改变网关侧权限和 Android 的 VALIDATED 能力，默认路由不一定变化。Flux 因此保留用户配置的订阅定时刷新，网络恢复事件只是额外触发；`fluxd subscribe` 可在认证后立即刷新。Flux 不通过持续联网探测来猜认证状态。

## Clash-Config 可以怎样应用

[Niklaus88/Clash-Config](https://github.com/Niklaus88/Clash-Config) 已经提供 sing-box 配置。研究时的配置声明需要 1.14.0+；当日最新稳定版是 1.14.1，其中 `http_clients` 和 `route.default_http_client` 已可表达。Flux 每次构建解析官方最新稳定版，兼容性由实际引擎和行为断言验证。

**可应用的是 DNS 与路由策略；原有 outbound 菜单保持不变。** 具体取舍如下：

| 内容 | 在 Flux 中如何使用 |
|---|---|
| 新式 DNS server、按域名分流、独立节点域名解析器 | 放在现有 `dns` 与解析设置中；保留你认可的校园/本地解析路径 |
| `http_clients`、规则集下载策略、remote binary rule-set | 使用支持它们的实际引擎；保持下载出口与节点启动依赖清晰 |
| 按服务划分的规则 | 将规则的 outbound 指向你已有的 `PROXY`、`DIRECT` 或地区组；不用搬来另一套菜单 |
| TUN、`auto_route`、`strict_route`、额外 mixed 入站 | 不能整段导入；Flux 的捕获入口由自身生成 |
| Clash YAML 的字段和覆盖配置的 JS | 不能直接放进 sing-box JSON；只借鉴明确的策略意图 |
| STUN 端口阻断、检测网站特判、全局 IPv4-only | 仅在你确实需要且理解影响时采用；不能推导出“所有应用零泄漏”，也不是校园网通用修复 |

适配步骤：

1. 保留自己的 `template.json` 及其 `outbounds`。
2. 选取确实需要的 DNS、rule-set、HTTP client 与路由规则；规则引用改为现有 tag，删去对上游独有菜单的引用。
3. 模板不声明 `inbounds`。FakeIP 地址避开 Flux 固定直连范围；已有默认值满足这个要求，不直接复制落在 `fc00::/7` 内的 IPv6 范围。
4. 保存后由 Flux 的候选事务交给实际引擎检查；诊断时运行 `fluxd check`。检查通过只证明配置接受，实际域名解析、规则集下载和校园网络连通还需观察。

远端 rule-set 也是启动依赖。若校园环境无法获取它，可以用 sing-box 原生的本地 rule-set 文件；这不需要 Flux 再维护一套规则下载器或备用状态。

本次只做来源核对和适配设计，没有把上游整份配置写入你的模板。具体提交、字段证据、许可及未验证范围见 [`网络参考研究`](../history/network-reference-research-2026-09-15.md)。
