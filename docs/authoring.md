# 制作规范：这套文档怎么写、怎么拆

本文管的是**文档本身的工程**：一份新写的东西该放在哪、用什么语言、怎么编号、怎么改。技术决策的判据在 `philosophy.md`，过程规范在 `governance.md`。

---

## AUTH-0 文档架构：目录即权威等级

### AUTH-0.1 定位规则

所有文档按一个问题归位：

> **这份文档和代码不一致时，谁错了？**

| 答案 | 层 | 位置 | 生命周期 |
|---|---|---|---|
| 合同错——它是蓝图的上游判据 | 判据 | `philosophy.md` | 不随版本 |
| 过程错 | 过程 | `governance.md`、`authoring.md` | 不随版本 |
| **代码错** | **合同** | `spec/` | 就地编辑，编号不动（AUTH-7.2） |
| 文档错，改文档 | 投影 | `guide/` | 随版本 |
| 都不错，它只记录当时发生了什么 | 记录 | `history/` | **只增不改** |
| 它描述的是还没发生的事 | 计划 | `plan/` | 会被做完 |

一个问题排完全部文档，而且对"新写的东西该放哪"永远有答案。写不出答案，说明这份材料混装了两层，应当先拆开。

### AUTH-0.2 为什么是目录而不是文件头标注

标注要靠人检查，目录不用。把 `history/` 里的东西写成合同、或者把合同放进 `guide/`，在文件树里当场显眼；而一行 `[层: 合同]` 的标注写错了没人会发现。

这是 PHIL-2「让无效状态不可表示」用在文档上：**路径本身携带权威等级**，`spec/blueprint.md` 不用打开就知道违反它意味着代码有 bug。

### AUTH-0.3 层与层之间的规矩

- **合同层只有一份，就地改**（AUTH-7.2）。不再叠加增量层。0.9.5 折叠完成前，`spec/` 里暂存的两份 0.9.x 增量仍然有效、冲突时取最新一层；折叠后它们移入 `history/`。
- **投影层不得创造合同**。`guide/` 里出现了合同里没有的约束，那是缺陷——要么补进 `spec/`，要么删掉。
- **记录层只增不改**。历史原话保留；它被后来的结论推翻时，在旁边注明被哪一条覆盖，不重写原文。
- **计划层会被做完**。做完的条目移入 `history/` 或直接删除，不留在 `plan/` 里假装还有效。

### AUTH-0.4 语言

依据是准确性，不是习惯。

| 层 | 语言 | 理由 |
|---|---|---|
| 判据、合同 | **英文** | 术语本来就是英文原生（`TC_ACT_UNSPEC`、`clsact`、`bpf_sk_assign`），中文散文夹英文标识符会持续产生 AUTH-6 在对付的混排问题；而且代码里数百处引用这两层 |
| 投影、面向用户 | 中文 | 读者是中文用户 |
| 过程 | 中文 | 读者只有维护者 |
| 记录 | 保持写作时的语言 | 历史不重写（AUTH-0.3） |

**不维护译本。** 一份手工翻译是同一批事实的第二份副本，没有任何机制保证同步，一定会分叉——PHIL-4 禁止的正是这个。需要哪种语言就用那一种写，不要两份。

### AUTH-0.5 根目录 `AGENTS.md`：只放路由，上限 80 行

这个项目几乎全部由 agent 写成，而 agent **每次会话都从零重建上下文**。`AGENTS.md` 是会话开始时无条件读入的那一份，因此它的每个 token 在**每次会话的每一轮**都要付一遍，永远。业界实测这类文件平均抬高推理成本 20% 以上。

由此得到两条硬规则：

1. **上限 80 行**，英文（它的读者是 agent，且大量引用合同层的英文标识符）。
2. **只放两样东西**：路由（做什么任务先读哪份文档）和**代码里看不出来的约束**。

第二条是判据：**如果一条信息能从代码或文档目录结构里看出来，它就不该占用这块地产。** 架构叙述、过程规范、设计理由一律留在 `docs/` 里按需读取——`AGENTS.md` 指路，不搬运知识。

值得写进去的反而是那些不成文的坑：宿主 PowerShell 5.1 会毁掉中文、`scratch/` 有真实凭据不得提交、章节号不得重排。这些错误 agent 会重复犯，而代码里找不到任何线索。

## AUTH-1 拆分原则：按读者拆，不按篇幅拆

`spec/blueprint.md` 一度到了 2881 行。直觉反应是"太长了，按章节切成十几个文件"，**但那是错的**。

技术核心（产品合同、平台事实、ABI、数据面、网络对象、engine、控制面、配置、加载器、封装）是**一张互相引用的密网**：§7.5 的不变量依赖 §8.4 的 sysctl 结论，§8.5.3 的 pref 策略依赖 §14.1 的性能预算，§8.5.4 的机制存在理由来自 §7.3 的 E1 分支。把它们切开不会让人更容易读懂，只会让两份文件慢慢长出互相矛盾的说法。

**真正的接缝在读者身上。** 判据是一句话：

> 如果两块内容**总是被同一个人在同一次工作中一起读**，它们就该在同一个文件里。

按这个判据，下面四块与技术核心是不同读者、不同时刻：

| 文件 | 谁在什么时候读 |
|---|---|
| `docs/spec/interaction.md` | 要改用户看得见的行为时：开关、配置、CLI、诊断包 |
| `docs/history/review-log.md` | 有人质疑某条断言的依据时，来查它是源码、实测还是推理 |
| `docs/history/phase0.md` | 要上机跑测试的人；以及想知道"这台设备实测出了什么"的人 |
| `docs/spec/failures.md` | 线上出问题、拿着一个错误码来查含义的人 |
| `docs/history/rejected-and-deferred.md` | 有人提议"为什么不做 X"时，来查 X 是否已被评估过 |

而**实现者**会把技术核心从头读到尾——所以它不拆。

### AUTH-1.1 拆分的代价必须被承认

拆完之后，`spec/blueprint.md` 里 `§16.3.5` 这样的引用会指向另一个文件。因此：

**章节编号是全局稳定标识符，跨文件不重编。** `§8.5.3` 无论最终落在哪个文件里都指同一件事，`rg "§8\.5\.3"` 永远能在全仓库找全它的引用。这条规则（GOV-6.2）是拆分能够安全进行的**唯一前提**；放弃它，拆分就会立刻制造一批悬空引用。

`docs/index.md` §4 维护 `§N → 文件` 的映射表，是编号到文件的唯一权威索引；`docs/README.md` 只负责把读者指过去，自己不复制这张表。`doc-check` 的章节映射检查逐行核对它。

## AUTH-2 每条断言必须标注它的证据等级

这套文档的价值全部来自"能不能被追查"。因此正文里的每条事实性断言，必须能被读者判断出它属于哪一类：

| 等级 | 写法要求 |
|---|---|
| **源码** | 给 `文件:行号`。内核源**必须带版本**（`v6.1 net/core/filter.c:2144`），因为语义会随版本变 |
| **实测** | 给设备、内核版本、日期；原始输出存进 `tools/phase0/results/` |
| **推理** | **必须显式写出"推断"字样**，并写清依赖哪些前提 |

三者之外的内容不进文档。"一般来说"、"通常"、"应该是"这类措辞，要么补上依据，要么删掉。

### AUTH-2.1 实测结论额外要标外推层级

按 `history/phase0.md` §16.3 的五层（AOSP 强制 / GKI 强制 / SoC 厂商 / OEM / 用户运行时）。**把 OEM 层观察当普适事实已经犯过一次**（"egress pref 1 是我们的"），所以这条是强制的，不是建议。

## AUTH-3 一律就地改，理由进对照表

详见 GOV-3。对文档形态的具体要求：

- **所有层都就地改正**，包括 `spec/blueprint.md`，不要在文末堆勘误，也不要另写一份文档描述差异（AUTH-7.2）。章节号保持不动。
- **改了什么看 `git log -p`，为什么改看对照表。** 这两件事各有一个家，不要再造第三份副本。
- `history/review-log.md` §0.6 维护 **原说法 / 实际 / 处置** 的历史对照表，所有推翻都进这张表。
- 被推翻的如果是一条编号决策，同时把它在 §0.3.0 / §21.0 状态登记里改成 `superseded` 并写明取代者。
- **结论对但理由错，要明确写出来。** 这类更正比结论错更重要，因为下一个决策会建立在错理由上。项目里已发生多次，全部按此处理，数量以 `history/review-log.md` 的实际行而不是散文计数为准。

## AUTH-4 写作要求

### AUTH-4.1 先给结论

每一节的第一句话是**结论**，不是背景。读者可能只读第一句。

反面：「TC filter 的优先级是一个需要考虑多方因素的问题。首先……」
正面：「pref 1 不是我们能预定的：Flux 按接口动态选择 preference，并用真实流量验证 filter 可达。」

### AUTH-4.2 表格用于可枚举的事实，散文用于论证

表格适合"字段 → 含义"、"情形 → 处置"。**不要**把论证塞进表格单元格——论证需要因果连接词，表格会把它们挤掉。

### AUTH-4.3 禁止的内容

| 禁止 | 原因 |
|---|---|
| 同一论证在多处重复 | 会分叉。改成一处 + 引用。研究依据指向 `history/review-log.md`，拒绝理由指向 `history/rejected-and-deferred.md` |
| 只有"待补充"的占位小节 | 制造虚假的完整感 |
| 为对称而补的章节 | 结构应服务内容 |
| 泛泛的最佳实践 | 不针对本项目的规则不会被遵守 |
| 未脱敏的实测输出 | 旧仓库把设备序列号提交进了 git 历史（F-07） |

### AUTH-4.4 规则要带疤

新增一条规矩时，**写清它防的是哪一次具体失误**。GOV-2.3 每一条都对应一次真实事故，这是有意的：抽象的规矩没人遵守，带疤的规矩才有人记住。

例：「脱敏规则禁止依赖 `\b`」后面必须跟「toybox 的 `sed -E` 不支持词边界且静默失效，已因此泄漏过一个地址」。

## AUTH-5 代码注释的规范

代码注释与设计文档是**两种东西**，混淆会同时毁掉两边。

| | 写什么 | 不写什么 |
|---|---|---|
| **设计文档** | 为什么这样设计、评估过哪些替代、依据是什么 | 逐行解释代码 |
| **代码注释** | 代码本身表达不了的**约束**，以及"如果你想改这里，先读 §X" | 复述代码在做什么、变更来源 |

数据面（`bpf/flux.bpf.c`）是唯一的例外：它的顶部契约注释**故意冗长**，因为那些不变量一旦被违反，症状是"静默地把用户流量泄漏到真实目的地"，而 verifier 与编译器都不会报错。**注释是那里唯一的防线。**

判断标准：注释里如果出现"因为某次修改"、"这里原来是"，那是在跟 reviewer 说话，应该进 commit message，不该留在代码里。

代码注释与标识符一律用英文——它们和源码在同一个命名空间里，中英混排会让 `rg` 变得不可用。

## AUTH-6 语言

**中文为主。** 专有名词、内核与 AOSP 的标识符、以及任何直译会产生歧义的地方，**保留英文原文**，不翻译、不加括号注释。

| 写 | 不写 |
|---|---|
| `TC_ACT_UNSPEC` | 「TC 动作未指定」 |
| `clsact` qdisc | 「clsact 队列规则」 |
| direct-action | 「直接动作」 |
| fail-open | 「失败开放」 |
| martian source 丢包 | 「火星源丢包」 |
| `bpf_sk_assign()` | 「BPF 套接字指派」 |

判据：**这个词在内核源码、AOSP 源码或 man page 里是什么样，就写成什么样。** 读者需要能用这个词直接去搜源码。

### AUTH-6.1 本节只管中文文档

语言归属由 AUTH-0.4 决定：判据层与合同层是英文，本节的中英混排规则不适用于它们——那两层通篇英文，不存在混排问题。

本节约束的是投影层、过程层与面向用户的文案。

面向用户的文案（`docs/spec/interaction.md` 里的示例输出、`flux.toml` 注释、README）同样中文为主，但那里的取向不同：**尽量不出现标识符**，需要时给出能查到它的命令。例：先写「该接口的捕获位置不可达」，再提示运行 `fluxd status` 或生成 `fluxd bugreport`；不要编造尚不存在的 `explain` 命令。

## AUTH-7.1 `guide/` 内部再按用途分，不混类

权威等级把 `guide/` 与 `spec/` 分开，但它不区分**同一层里读者想干什么**。Diátaxis 的核心主张是：混类是文档不清晰的首要原因——一个人「想理解」和「想解决」时需要的东西不一样，写在一起两边都不好用。

因此 `guide/` 的每份文档只承担一种用途，文件名里已经标出：

| 用途 | 读者在干什么 | 文件 |
|---|---|---|
| explanation | 想理解：这是什么、为什么这么设计、有什么边界 | `introduction.md`、`architecture.md` |
| how-to | 想解决：怎么装、怎么配、坏了怎么办 | `how-to.md` |

**判据：如果一段内容删掉之后，"想理解"的读者不受影响，那它属于 how-to；反之属于 explanation。** 两类之间用链接连接，不复制内容。

tutorial 与 reference 两类暂缺：前者用不上（安装即全部流程，how-to 已覆盖），后者由 `spec/` 承担。

## AUTH-7.2 只有一份蓝图：增量机制已废除

**`spec/blueprint.md` 是唯一的规范性蓝图，就地编辑。** 不再产生 `blueprint-0.9.x.md` 这类增量文件。

废除的理由，不是嫌麻烦，是它违反 PHIL-4：

增量机制当初为了「不回写历史」而存在。但历史已经有两个更合适的家——**git 保存了每一个历史状态**（改了什么），**`history/review-log.md` 保存了每一次推翻的原说法/实际/处置**（为什么改）。增量蓝图是这两件事的第三份副本，代价却由每个读者承担：同一条规则要在脑子里叠三层，"§8.5，经 R091-05 修订，再经 R092-11 修订"。同一个事实有了三个可写的家。

新规则：

1. 规范性变更**直接改 `spec/blueprint.md`**，在原章节就地改写。
2. **章节号永不复用、永不重排**——它们被代码引用（当前 327 处，44 个文件）。插入新内容用新的子编号，删除内容留下指向去处的存根。
3. **变更理由进 `history/review-log.md`**；推翻既有结论的，按 GOV-3 记入更正对照表。
4. **差异看 `git log -p docs/spec/blueprint.md`**，不靠另写一份文档描述差异。
5. 版本号标注在蓝图开头「本文规定哪个版本」，随发布更新。

`R09x-NN` 这套编号在 0.9.5 折叠完成后退役：不再新发，已有的由 0.9.5 的对照表映射到承载它的 §。

## AUTH-7.3 再版一份文档时先做保真核对

整体重写一份既有文档——翻译、折叠增量、重组——是**整体重新生成**，而整体重新生成会丢掉历次迭代积累的细化，且结果读起来毫无破绽，因此丢失不可见。

散文无法机械比对，但其中四样可以，而且正是最费功夫得到的那四样：证据引用（`FileSystem.kt:524-625`）、交叉引用（`§8.5.3`）、标识符（`D18`、`C9`）、数值常量（`65536`、`198.51.100.1`）。

```
cargo xtask fidelity <再版前> <再版后>
```

它列出前者有而后者没有的每一项。**再版可以合法地删掉其中任何一项，但必须逐条说明为什么**——这是核对，不是门禁。
