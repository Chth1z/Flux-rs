# 制作规范：这套文档怎么写、怎么拆

本文管的是**文档本身的工程**。过程规范在 `docs/governance.md`，技术合同在 `docs/blueprint.md`。

---

## 1 拆分原则：按读者拆，不按篇幅拆

`blueprint.md` 一度到了 2881 行。直觉反应是"太长了，按章节切成十几个文件"，**但那是错的**。

技术核心（产品合同、平台事实、ABI、数据面、网络对象、engine、控制面、配置、加载器、封装）是**一张互相引用的密网**：§7.5 的不变量依赖 §8.4 的 sysctl 结论，§8.5.3 的 pref 策略依赖 §14.1 的性能预算，§8.5.4 的机制存在理由来自 §7.3 的 E1 分支。把它们切开不会让人更容易读懂，只会让两份文件慢慢长出互相矛盾的说法。

**真正的接缝在读者身上。** 判据是一句话：

> 如果两块内容**总是被同一个人在同一次工作中一起读**，它们就该在同一个文件里。

按这个判据，下面四块与技术核心是不同读者、不同时刻：

| 文件 | 谁在什么时候读 |
|---|---|
| `docs/evidence/review-log.md` | 有人质疑某条断言的依据时，来查它是源码、实测还是推理 |
| `docs/verification/phase0.md` | 要上机跑测试的人；以及想知道"这台设备实测出了什么"的人 |
| `docs/reference/failures-and-status.md` | 线上出问题、拿着一个错误码来查含义的人 |
| `docs/decisions/rejected-and-deferred.md` | 有人提议"为什么不做 X"时，来查 X 是否已被评估过 |

而**实现者**会把技术核心从头读到尾——所以它不拆。

### 1.1 拆分的代价必须被承认

拆完之后，`blueprint.md` 里 `§16.3.5` 这样的引用会指向另一个文件。因此：

**章节编号是全局稳定标识符，跨文件不重编。** `§8.5.3` 无论最终落在哪个文件里都指同一件事，`rg "§8\.5\.3"` 永远能在全仓库找全它的引用。这条规则（`governance.md` §6.2）是拆分能够安全进行的**唯一前提**；放弃它，拆分就会立刻制造一批悬空引用。

`docs/README.md` 维护一张 `部分 → 文件` 的映射表，是编号到文件的唯一权威索引。

## 2 每条断言必须标注它的证据等级

这套文档的价值全部来自"能不能被追查"。因此正文里的每条事实性断言，必须能被读者判断出它属于哪一类：

| 等级 | 写法要求 |
|---|---|
| **源码** | 给 `文件:行号`。内核源**必须带版本**（`v6.1 net/core/filter.c:2144`），因为语义会随版本变 |
| **实测** | 给设备、内核版本、日期；原始输出存进 `tools/phase0/results/` |
| **推理** | **必须显式写出"推断"字样**，并写清依赖哪些前提 |

三者之外的内容不进文档。"一般来说"、"通常"、"应该是"这类措辞，要么补上依据，要么删掉。

### 2.1 实测结论额外要标外推层级

按 `blueprint.md` §16.3 的五层（AOSP 强制 / GKI 强制 / SoC 厂商 / OEM / 用户运行时）。**把 OEM 层观察当普适事实已经犯过一次**（"egress pref 1 是我们的"），所以这条是强制的，不是建议。

## 3 更正要就地改，并留下对照

详见 `governance.md` §3。对文档形态的具体要求：

- 更正**写在原地**，不要在文末堆勘误。
- `blueprint.md` §0.5 维护一张 **原说法 / 实际 / 处置** 的对照表，所有推翻都进这张表。
- **结论对但理由错，要明确写出来。** 这类更正比结论错更重要，因为下一个决策会建立在错理由上。已发生四次，全部按此处理。

---

## 4 写作要求

### 4.1 先给结论

每一节的第一句话是**结论**，不是背景。读者可能只读第一句。

反面：「TC filter 的优先级是一个需要考虑多方因素的问题。首先……」
正面：「pref 1 不是我们能预定的：厂商已经占了它，而 tc 的 pref 最小就是 1。」

### 4.2 表格用于可枚举的事实，散文用于论证

表格适合"字段 → 含义"、"情形 → 处置"。**不要**把论证塞进表格单元格——论证需要因果连接词，表格会把它们挤掉。

### 4.3 禁止的内容

| 禁止 | 原因 |
|---|---|
| 同一论证在多处重复 | 会分叉。改成一处 + 引用。已处理过：CHANGELOG 里的架构变更理由压成一句指向 §0/§19 |
| 只有"待补充"的占位小节 | 制造虚假的完整感 |
| 为对称而补的章节 | 结构应服务内容 |
| 泛泛的最佳实践 | 不针对本项目的规则不会被遵守 |
| 未脱敏的实测输出 | 旧仓库把设备序列号提交进了 git 历史（F-07） |

### 4.4 规则要带疤

新增一条规矩时，**写清它防的是哪一次具体失误**。`governance.md` §2.3 每一条都对应一次真实事故，这是有意的：抽象的规矩没人遵守，带疤的规矩才有人记住。

例：「脱敏规则禁止依赖 `\b`」后面必须跟「toybox 的 `sed -E` 不支持词边界且静默失效，已因此泄漏过一个地址」。

## 5 代码注释的规范

代码注释与设计文档是**两种东西**，混淆会同时毁掉两边。

| | 写什么 | 不写什么 |
|---|---|---|
| **设计文档** | 为什么这样设计、评估过哪些替代、依据是什么 | 逐行解释代码 |
| **代码注释** | 代码本身表达不了的**约束**，以及"如果你想改这里，先读 §X" | 复述代码在做什么、变更来源 |

数据面（`bpf/flux.bpf.c`）是唯一的例外：它的顶部契约注释**故意冗长**，因为那些不变量一旦被违反，症状是"静默地把用户流量泄漏到真实目的地"，而 verifier 与编译器都不会报错。**注释是那里唯一的防线。**

判断标准：注释里如果出现"因为某次修改"、"这里原来是"，那是在跟 reviewer 说话，应该进 commit message，不该留在代码里。

代码注释与标识符一律用英文——它们和源码在同一个命名空间里，中英混排会让 `rg` 变得不可用。

---

## 6 语言

**中文为主。** 专有名词、内核与 AOSP 的标识符、以及任何直译会产生歧义的地方，**保留英文原文**，不翻译、不加括号注释。

| 写 | 不写 |
|---|---|
| `TC_ACT_UNSPEC` | 「TC 动作未指定」 |
| `clsact` qdisc | 「clsact 队列规则」 |
| direct-action | 「直接动作」 |
| fail-open | 「失败开放」 |
| martian source 丢包 | 「火星源丢包」 |
| `bpf_sk_assign()` | 「BPF 套接字指派」 |

判据：**这个词在内核源码、AOSP 源码或 man page 里是什么样，就写成什么样。** 读者需要能用这个词直接去搜源码。

面向用户的文案（`docs/ux.md` 里的示例输出、`flux.toml` 注释、README）同样中文为主，但那里的取向不同：**尽量不出现标识符**，需要时给出能查到它的命令。例：不写 `tc_chain_shadowed`，写「位置被占用」并附 `fluxd explain wlan0`。

## 7 目标结构

```
docs/
  README.md                          索引：部分 → 文件 的权威映射
  blueprint.md                       规范性技术合同（实现者从头读到尾）
  architecture.md                    面向新读者的导览
  governance.md                      过程规范：决策权、证据纪律、验证门
  authoring.md                       本文
  ux.md                              交互与体验设计
  evidence/
    review-log.md                    独立复核记录 + 更正对照表（原 §0）
  verification/
    phase0.md                        Phase 0 十问 + 实测结果 + 外推分层（原 §16）
  reference/
    failures-and-status.md           失败矩阵 + status/错误码规格（原 §23、§24）
  decisions/
    rejected-and-deferred.md         被拒方案 + 延期项 + 待确认事项（原 §19、§21、§22）
tools/phase0/
  README.md                          探针工具说明
  observe.sh                         只读观测探针
  q10-*.sh                           会改状态的测试（需授权，带 cleanup trap）
  results/                           脱敏后的实测原始记录，只增不改
```

**`blueprint.md` 保持规范性地位。** 其它文档与它冲突时，以它为准；发现冲突要改的是有分歧的那一方，不是加一条"两者都对"。
