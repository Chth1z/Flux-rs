# 交互与使用体验设计

规范性技术合同在 `docs/blueprint.md`。本文只管**用户看到什么、能做什么、出问题时怎么自救**。

---

## 0 先承认这个产品的体验难点

Flux 是一个没有自己 App 的 root 模块。它的交互面被三件事框死：

1. **`action.sh` 只有一个按钮**，STDOUT 显示在管理器 UI 里、STDERR 被丢弃、STDIN 不可用（§13.2.1）。
2. **选 app 天然是个列表选择问题**，而用户认得的是 app 名字，`packages.list` 里只有包名。手机上手编 TOML 填 `0:com.example.foo` 是糟糕的体验。
3. **这个产品的失败模式很多且很技术**（§2.2.3 七条边界、§23 失败矩阵）。如果只把 `tc_chain_shadowed` 这种错误码抛给用户，等于没有反馈。

设计目标按优先级排序，冲突时按此裁决：

**① 不能把设备弄成没网 → ② 用户能知道现在是否真的在工作 → ③ 出问题时能自己查出原因 → ④ 选 app 不痛苦 → ⑤ 功能丰富。**

第 5 位是最后一位。这个顺序是有意的：一个只能代理 3 个 app 但状态永远诚实的产品，比一个功能全面但用户搞不清有没有生效的产品好。

---

## 1 分层交互面

不同 root 管理器的能力差别很大，所以交互面分三层，**每层都能独立完成核心任务**，上层只是更舒服。

| 层 | 载体 | 可用范围 | 能做什么 |
|---|---|---|---|
| **0** | `action.sh` + `module.prop` 的 `description` | Magisk ≥ v28.0 / KernelSU / APatch | 一键开关 + 一行状态。**不装任何东西也能用** |
| **1** | WebUI（`webroot/`） | KernelSU / APatch | 选 app、看状态、跑诊断 |
| **2** | `fluxd` CLI + `flux.toml` | 全部（需终端或 adb） | 全部能力，含机器可读输出 |

**层 0 必须自足。** Magisk 用户没有 WebUI，所以"装上之后能开、能关、能看出状态"必须只靠 `action.sh` 完成。

## 2 层 0：一个按钮和一行字

### 2.1 状态行（`module.prop` 的 `description`）

管理器在 `action.sh` 结束后会重读 `module.prop`（§13.2.1），所以 `description` 是**唯一一个不需要用户操作就能看到的状态出口**。它必须一眼读懂，格式固定：

```
description=[状态] 摘要 · 细节
```

| 状态 | 示例 |
|---|---|
| 未配置 | `[未配置] 还没有选择任何应用 · 点按操作按钮查看如何开始` |
| 正常 | `[运行中] 3 个应用 · 经 wlan0 · 41 条 TCP / 388 个 UDP` |
| 部分可用 | `[部分可用] 3 个应用 · wlan0 未接管（被系统占用）· 蜂窝正常` |
| 未激活 | `[未激活] 内核缺少 BPF 能力 · 点按查看详情` |
| 已停用 | `[已停用] 点按启用` |

三条硬规则：

- **不显示"成功/失败"，显示"现在什么状态"。** 用户关心的是当下能不能用。
- **"部分可用"必须单列。** 这是本设计最常见的真实状态（某个 interface 被厂商 filter 遮挡、或刚重连还没重挂 filter），把它归进"正常"是欺骗，归进"失败"是误导。
- **不放技术错误码。** 错误码给 `status` 和 WebUI，不给这一行。

### 2.2 按钮的行为

一个按钮要承载"启用/停用/看详情"三件事，靠**当前状态决定语义**：

| 当前状态 | 按钮做什么 |
|---|---|
| 已停用 | 启用，并输出启用结果 |
| 运行中 | 停用 |
| 部分可用 | **不切换**，输出诊断（用户更可能想知道为什么，而不是关掉它） |
| 未激活 | **不切换**，输出为什么不能激活 + 怎么处置 |
| 未配置 | 输出如何选 app（含 WebUI 入口或 TOML 路径） |

"部分可用"和"未激活"时不切换是刻意的：那两种状态下用户的意图几乎一定是"查问题"。要强制切换可以再按一次（第二次的状态已变）。

### 2.3 输出文案

STDOUT 会显示在管理器里，空间有限。**先结论，再原因，最后动作。**

```
Flux-rs 部分可用

3 个应用已选择，蜂窝网络正常接管。
Wi-Fi（wlan0）未接管：三星的流量统计程序占用了我们需要的
位置，我们的程序装上了但收不到数据包。

这不是配置错误，也不会影响上网。切到蜂窝网络即可正常代理。
详情：fluxd explain wlan0
```

规则：**不出现 `tc_chain_shadowed` 这种标识符**，但要给出能查到它的命令。用户不需要懂机制，但需要有路径深入。

## 3 层 1：WebUI

KernelSU 与 APatch 支持模块自带 `webroot/index.html`。这是解决"选 app"的地方。

### 3.1 只做四件事

刻意窄。`blueprint.md` §22.3 拒绝了"自有 Clash 代理层"——代理规则、节点、订阅全部归 sing-box 自己的 Clash API，WebUI **不碰**。它只管 Flux 自己的那部分：

1. **应用选择**：列表 + 搜索 + 已选置顶。
2. **状态**：§2.1 那一行的展开版，逐 interface 显示。
3. **诊断**：`fluxd status --json` 的人类可读渲染 + 一键复制原始 JSON。
4. **开关**。

### 3.2 应用列表怎么拿到名字

`packages.list` 只有包名（D8）。要显示用户认得的名字需要 PackageManager，而 D8 明确拒绝了 daemon 依赖 binder。

**这两件事不矛盾，边界在于时机**：D8 的理由是"`service.sh` 在 late-start 运行时 `system_server` 可能未就绪，会引入启动顺序依赖"。而 WebUI 是**用户主动打开**的，那时 `system_server` 必然在跑。

所以规则是：

- **daemon 的启动路径永不碰 binder**，只读 `packages.list`（D8 不变）。
- **WebUI 按需调 `pm list packages -3` / `cmd package` 取标签**，失败就退回显示包名。**取不到名字只是体验降级，不能影响功能。**

列表默认只显示第三方 app（`-3`）。系统 app 需要显式切换才显示，并在切换处写明风险——选中 `system_server` 之类的后果是设备失联（`appId` 范围硬限制已从结构上挡住，见 D9，但 UI 不该引导用户往那边走）。

### 3.3 选择的粒度

内部标识是 `userId:packageName`（§1.1）。UI 上：

- 单用户设备**不显示** `userId`，直接列 app。
- 存在工作资料/多用户时，按用户分组，并显示"同一个 app 在不同用户下是两个独立选择"。
- **shared UID 必须显式提示**：选中一个共享 UID 的 app，会连带捕获同 UID 的其它 app。UI 要把连带的 app 列出来让用户确认，不要静默生效。

最后一条不是细节。shared UID 的连带效应是"我只选了 A，为什么 B 的流量也走代理了"这类困惑的唯一来源。

## 4 层 2：CLI

### 4.1 命令集

| 命令 | 输出 |
|---|---|
| `fluxd status` | 人类可读状态 |
| `fluxd status --json` | 机器可读（§24 规定字段） |
| `fluxd check` | 只校验配置与能力，不改状态 |
| `fluxd enable` / `disable` | 持久化开关 |
| `fluxd reload` | 重读配置并收敛 |
| `fluxd explain <目标>` | **诊断，见 §4.2** |

### 4.2 `explain`：本设计最重要的一个命令

这个产品有七条公开的不可消除边界（§2.2.3）。用户一定会遇到"这个 app 为什么没走代理"。没有 `explain`，答案只能靠猜。

`fluxd explain <package|uid|interface>` 逐条回答，**按判定顺序输出，在第一个否决处停止并说明**：

```
$ fluxd explain com.example.app

应用            com.example.app
UID             10287（用户 0）
是否选中        是
共享 UID        否

当前接管路径
  wlan0         未接管 —— 位置被占用
                我们的程序在 TC egress pref 2，但 pref 1 上的
                prog_semUidBPF_schedcls_egress_tsm_ether 终止了处理链。
                存活验证：接口发出 12043 个包，我们的程序收到 0 个。
  rmnet_data0   已接管 —— pref 2，存活验证通过

已知不会被接管的情况
  · 该应用通过 DownloadManager 下载的流量（归属为下载器的 UID）
  · 该应用走 VPN 时的流量（当前无 VPN）
  · 加密 DNS（当前 Private DNS = opportunistic，明文查询会被接管）

结论
  Wi-Fi 下不生效，蜂窝下生效。原因是厂商程序占位，不是配置问题。
```

设计要求：

- **只报事实与实测值，不猜。** "存活验证：发出 12043，收到 0" 比 "可能被遮挡" 有用得多。
- **列出"已知不会被接管的情况"**，即使当前没触发。这是把 §2.2.3 从文档搬到用户眼前的唯一办法。
- **区分"配置问题"和"环境限制"。** 前者用户能改，后者不能。混在一起会让用户徒劳地反复改配置。

### 4.3 配置文件

`flux.toml` 面向手编，因此：注释即文档、字段名用完整单词不用缩写、拒绝未知键并**指出最接近的合法键名**（拼错一个字段而静默失效是最糟的失败）。

## 5 第一次使用

装完模块重启后，状态是 `[未配置]`。**这不是错误状态**，UI 措辞不能像报错。

引导路径按管理器分岔：

- KernelSU / APatch：`action.sh` 输出指向 WebUI。
- Magisk：`action.sh` 输出 `flux.toml` 的完整路径 + 一个可直接抄的两行示例 + 提示"改完点这个按钮"。

**不做**开机弹窗、通知、引导流程。这是 root 模块，用户是主动来找它的。

## 6 出问题时怎么自救

这是**最高优先级**的体验要求，因为最坏情况是设备没网而用户手上没有电脑。

### 6.1 设计上的保证

| 保证 | 出处 |
|---|---|
| 未入场的失败一律走直连，不影响上网 | §2.2.1 fail-open |
| `active` 未发布前不改变任何流量走向 | §8.5.4 |
| 全局 sysctl 永不被写 | §8.4 |
| `clsact` qdisc 永不删除（不破坏 tethering / CLAT） | §8.5 |
| 单实例锁由内核在进程死亡时释放 | §11.2 |

### 6.2 恢复路径，按代价从低到高

1. **管理器里点一下按钮**（停用）。不需要终端。
2. **在管理器里禁用模块**并重启。Flux 的对象随 `fluxd` 退出被清理；`clsact` 与系统对象不受影响。
3. **卸载模块**。`uninstall.sh` 必须清理**模块目录之外**的全部状态：TC filter（不是 qdisc）、`ip rule`、路由表项、per-device sysctl、veth（§13.2）。
4. **Magisk 安全模式 / KernelSU 关闭模块**。所有模块不加载，设备必定恢复。

**第 4 条必须写进 README。** 它是最终保证，用户需要事先知道它存在。

### 6.3 一条明确的非目标

**不实现"网络看门狗自动回滚"。** 理由与 §2.2.3(3) 拒绝 heartbeat 同源：判断"网络是否正常"需要主动探测，而探测本身会产生流量、需要选择探测目标、并在离线时误判。一个会误判的自动回滚比没有自动回滚更糟——它会在用户正常使用时把代理关掉。

代替方案是把上面四条恢复路径写清楚、让状态永远诚实。

## 7 刻意不做

| 不做 | 理由 |
|---|---|
| 自有 Clash 代理层 / 节点管理 UI | sing-box 自带 Clash API 与 observability，重复造只增加攻击面（§22.3） |
| 开机通知 / 常驻通知 | 需要 App 或 binder 依赖；root 模块的用户是主动来找的 |
| 网络自动回滚看门狗 | §6.3 |
| 流量图表 | 需要持续采样，与"计数器只在决策边沿递增"（§6）冲突 |
| 按域名/规则选择 | 这是 sing-box 的职责，Flux 只做 UID 粗分流（§1.4） |
| 独立 Android App | 属新产品线；控制协议已是版本化 JSON，将来加不需要改造（§22.2） |

---

## 8 待所有者决定

1. **要不要做 WebUI（层 1）。** 它是解决"选 app"的唯一体面办法，但只覆盖 KernelSU/APatch，且增加一个 HTML/JS 交付面与相应的审计负担。不做的话 Magisk 与 KernelSU 用户体验一致（都手编 TOML），做的话两者分化。
2. **文案语言。** 上面示例是中文。要不要同时出英文，以及默认跟随什么（系统语言在 root 模块里不易可靠获取）。
3. **`explain` 的深度。** 现在的示例把实测数字（"发出 12043，收到 0"）直接给用户。信息量大但也可能显得吓人。
